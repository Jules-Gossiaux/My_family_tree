# Revue de code — simple_family_tree

Revue faite sur l'intégralité de `src/` (~10 977 lignes, 26 fichiers) hors `legacy/`, plus `package.json`, `tsconfig.json`, `README.md`, `.gitignore`. Le build (`tsc --noEmit && vite build`) passe. Aucun `any`, aucun `@ts-ignore`, aucun TODO nulle part dans `src/`. Les problèmes les plus graves ne sont pas dans la qualité du code, qui est franchement bonne pour un projet personnel, mais dans la persistance : écriture silencieuse, pas de filet en cas d'échec, pas de concurrence.

---

## 1. Architecture et structure

**Verdict général : la séparation domain / layout / components est réelle et respectée.** Le domaine est pur (fonctions immuables, aucun import React), le layout est câblé sur `TreeLayout` générique, les composants ne manipulent les données qu'à travers `operations`/`directories`/`lifeEvents`. C'est mieux que beaucoup de projets personnels. Les vrais problèmes sont la localisation de la logique d'UI dans App.tsx et quelques fuites du domaine vers l'affichage.

**Important — App.tsx concentre trois rôles (orchestrateur, fabrique de textes d'UI, gestionnaire clavier global).**
- `hintFor` (`App.tsx:51-88`) et surtout `resolutionView` (`App.tsx:561-776`) sont ~215 lignes de prose française métier (titres, descriptions, options recommandées) dans un `useMemo`. Ce sont les textes des dialogues de résolution de conflits — ils appartiennent à un module dédié (`domain/conflictMessages.ts`), testables sans React.
- 15 `useState`/`useRef` de premier niveau (`App.tsx:100-148`) : `data`, `selectedId`, `dialog`, `pending`, `layout`, `grouping`, `fitSignal`, `search`, `searchOpen`, `focusRequest`, `toast`, `directoryOpen`, `eventDialog`, `portraits` + trois refs. Aucun `useReducer` alors que `dialog`/`pending`/`fitSignal` mutent toujours ensemble dans `applyMutation` (`App.tsx:290-297`) et `handleResolution` (`App.tsx:330-350`). Le risque concret : `setDialog(null)` et `setPending(null)` oubliés dans un futur chemin d'ajout, ou des états désynchronisés (par ex. `dialog` fermé mais `existingOptions` recalculé avec l'ancien `dialog.kind`).
- `SidePanel` reçoit 16 callbacks (`SidePanel.tsx:24-43`), dont `onChange` qui expose la mutation arbitraire du document entier — c'est du couplage de fait vers n'importe quel composant.

**Important — deux chaînes de mutation concurrentes pour la fiche.**
- `SidePanel.patchPerson` (`SidePanel.tsx:97-106`) fait un spread direct du patch + `updatedAt: now()`, **sans** `touch()` ni `syncDefaultLifeEvents()`, tandis que `onUpdate` → `operations.updatePerson` fait les deux. Aujourd'hui `patchPerson` ne sert qu'à `cemeteryPlaceId`, donc rien ne casse — mais la moindre réutilisation pour un champ de date créera un événement par défaut désynchronisé, silencieusement. Un seul point d'entrée (`updatePerson` avec un patch étendu) élimine le piège.

**Important — fuite de responsabilité du layout :** `classic.ts` construit les libellés d'info-bulles des pastilles (`UnionInfo.title`, ~`classic.ts:255-265`, via `UNION_STATUS_LABELS` et `personLabel`). Un moteur de placement devrait sortir de la géométrie pure, pas du texte d'UI.

**Mineur — `layout.ts:51-56`** : `computeLayout` est déclarée `async` « pour ne pas changer le contrat de l'interface » mais le calcul est synchrone (le commentaire l'admet). C'est un faux asynchronisme : il bloque le thread principal comme un appel sync, tout en ajoutant un saut de tâche qui décale le rendu d'une frame. Le `useEffect` de `App.tsx:180-192` gère un `cancelled` qui protège contre un cas qui ne peut plus arriver depuis la suppression d'ELK.

**Mineur — `EVENT_TYPES`, `STATUSES`, `LINKS`… sont définis deux fois** : `types.ts` (constantes exportées) et `repository.ts:574-640` (listes dupliquées pour la validation d'import). Réutiliser les constantes de `types.ts` supprimerait ~60 lignes et le risque de divergence quand un type sera ajouté.

## 2. Qualité du code

**Le typage est globalement strict et propre :** `strict: true`, zéro `any`, zéro cast injustifié dans le domaine. Les réserves :

**Important — types lâches en périphérie.** `EventParticipant.role: string` (`types.ts:117`) alors que `PARTICIPANT_ROLES` est une liste fermée — ce devrait être un type union. `PARTICIPANT_ROLE_LABELS: Record<string, string>` (`types.ts:130`) perd toute vérification. Et une dizaine de `as` de conversion d'`event.target.value` (`App.tsx:701`, `SidePanel.tsx:246,253`, `EventDialog.tsx:107,255`…) : valeurs contrôlées par des `<select>`, donc sans risque immédiat, mais non validées au runtime.

**Important — `parseFuzzyDate` (domain/dates.ts) est la partie la plus fragile du domaine, sans test.** Le parser de dates floues combine 26 lignes de regex de qualificatifs, un `if (day && year) { /* commentaire seulement */ }` à bloc vide (`dates.ts:152-154`) — branche morte — et des heuristiques observables sur des cas limites :
- « 12/03/1890 » passe par `frenchNumeric` (`dates.ts:97-105`) mais « vers 12/03 » ne prend pas le chemin ISO et retombe dans la séparation jour/mois (`dates.ts:158-172`), où `\d{1,2}` ambivalent jour/mois est arbitré par une règle « ≤ 12 → mois » (`dates.ts:175-180`).
- « 1890-05 » ou « 05/1890 » (dates partielles, courantes en généalogie) : aucune branche dédiée, décomposition imprévisible.
- Le commentaire mort `// « 12 mars 1890 » : le « 12 » trouvé plus haut est bien le jour.` (`dates.ts:150-152`) documente une branche `if (day && year) {}` qui ne fait rien.

**Mineur — duplication de logique label :** `nameOf` est défini presque à l'identique dans `App.tsx:564-568`, `SidePanel.tsx:87-92` et inline dans `classic.ts`. Un `personLabelById(data, id)` mutualisé suffirait.

**Mineur — `searchResults` duplique prénom/nom dans la concaténation** (`App.tsx:259-263` : `${lastName} ${firstName}` matche déjà via `includes` sur la première forme, redondance inutile mais innocente).

**Mineur — `EventDialog.tsx:194,259` : listes de participants/citations clées par index** (`key={index}`) — classique source de désync d'état si la structure est réordonnée un jour.

La gestion d'erreurs est cohérente (try/catch + `console.warn` + fallback) mais **systématiquement silencieuse pour l'utilisateur** — voir point 3.

## 3. Persistance et robustesse — le point critique du projet

**Bloquant — l'échec de sauvegarde est invisible et l'application redémarre sur un arbre vide.**
`LocalFamilyRepository.save` (`repository.ts:63-68`) :
```ts
} catch (error) {
  console.warn('Impossible de sauvegarder les données locales.', error);
}
```
`localStorage` jette sur dépassement de quota (~5 Mo) ou en navigation privée restreinte. Et côté lecture : `load` attrape tout et renvoie `emptyFamily()` (`repository.ts:36-41`) — l'utilisateur avec un arbre de 200 personnes et un quota dépassé voit un écran « Chargement… » puis un arbre vide, sans jamais être prévenu que ses données sont perdues. Trois remèdes pas chers : 1) faire échouer `save` et afficher un bandeau persistant ; 2) distinguer « clé absente » de « clé corrompue » dans `load` et ne jamais remplacer un document existant par `emptyFamily()` sans confirmation ; 3) garder une copie de secours `STORAGE_KEY:backup` écrite avant chaque écrasement.

**Bloquant — les médias ne sont jamais cohérents avec le document.** À l'import v3 (`parseFamilyDocument`, `repository.ts:111-140`), les `dataUrl` sont poussés dans IndexedDB **avant** d'accepter ou non le document ; en cas d'erreur de validation par-dessus, les octets sont orphelins. À la suppression (`MediaGallery.remove`, `MediaGallery.tsx:158-162`), `mediaStore.delete` est déclenché **avant** `onChange(deleteMedia(...))` sans confirmation que la mutation a été appliquée. Et si l'utilisateur ferme l'onglet entre les deux, ou si l'édition d'un champ texte fait rollback, les octets sont perdus pour de bon. Une suppression atomique (document d'abord, GC des octets orphelins au chargement) serait plus sûre.

**Important — aucun garbage-collect des octets.** Rien ne nettoie les blobs : `clear()` (`repository.ts:70-77`) et `deleteMedia` existent, mais un média retiré par un import écrasant (import d'une autre famille par-dessus) ne supprime pas les clés IndexedDB correspondantes. Sur une longue utilisation, la base de médias ne fait que grossir.

**Important — concurrence multi-onglets : rien.** Deux onglets sur l'app → deux copies de `data` en mémoire, dernier `setItem` gagne, écrasant les modifications de l'autre sans aucun conflit visible. L'événement `storage` n'est jamais écouté (aucune occurrence dans `src/`). Même sans verrou complet, une simple détection (event `storage` + compteur d'onglet) et un avertissement suffiraient.

**Important — la sauvegarde s'exécute à chaque frappe.** L'effet `App.tsx:160-162` sérialise et écrit **tout** le document (`JSON.stringify` complet) à chaque `setData`, donc à chaque caractère tapé dans un champ texte. Pas de debounce ni de comparaison structurelle. À combiner avec le `useMemo` de portraits qui recrée **toutes** les object URLs à chaque mutation (`App.tsx:196-237`, dépendance `[data]`) : taper « Martin » dans une note réécrit le localStorage et reconstruit tous les blobs en URL — inutile et coûteux en jank dès qu'il y a plusieurs dizaines de portraits.

**Important — `mediaStore` avale toutes les erreurs et pollue la mémoire.** `transaction()` résout `undefined` sur toute erreur (`mediaStore.ts:62-63`, `catch { resolve(undefined) }`) et le `catch` de `MediaGallery.handleFiles` (`MediaGallery.tsx:120`) n'est donc **jamais** atteint : l'échec d'écriture d'un média est converti en « média absent », silencieusement. Par ailleurs `put` remplit la Map `memory` en plus d'IndexedDB (`mediaStore.ts:72`) et ne la vide jamais — les blobs restent en mémoire pour la durée de vie de l'app, en double avec IndexedDB.

**Mineur — `validateFamilyData` est un modèle du genre** (normalisation défensive, dédoublonnage, purge des références pendantes, `pruneGhostUnions`) : c'est le fichier le plus précieux du projet. Dommage qu'il n'ait pas de test (voir point 4).

**Mineur — export bloquant en mémoire :** `exportFamilyBundle` (`repository.ts:82-100`) construit un unique `JSON.stringify` avec toutes les photos en data URL (×1,33 de taille). Avec 100 photos de 3 Mo, ça fait ~400 Mo de chaîne en un seul appel — un `Blob` construit par parties serait plus robuste.

## 4. Tests — aucun. Confirmé.

**Important (dette la plus coûteuse à terme).** `package.json` n'a pas de script `test`, aucune dépendance vitest/jest, aucun fichier `*.test.*` sous `src/`. Détail instructif : `legacy/tests/` en contient 17 (dates, layout, relations, life-events, migration…) — la couverture **existait** dans l'ancienne version et a été jetée au portage. Les commentaires du code actuel invoquent même des tests qui n'existent pas (`directories.ts:327` : « Utilisé par les tests et l'UI » ; `repository.ts:80` : « conservé pour… les tests »).

Ordre de priorité pour les écrire (tous testables sans rendu React, avec vitest seul) :
1. **`dates.ts` / `parseFuzzyDate` + `composeFuzzyDate`** — round-trip sur les formats du `placeholder` (« vers 1890 », « avant 1914 », « 12 mars 1890 »), les ISO, les dates partielles et les formats hérités. C'est du parsing regex fragile au risque de déformation silencieuse des données.
2. **`operations.ts` — `planRelation` / `resolveRelation`** : c'est la règle produit « toujours demander, ne jamais fusionner » (README). Chaque combinaison kind × union incomplète × doublon × `step`/`adoptive`/`legal` est un scénario de perte de filiation — les pires bugs seraient invisibles à l'œil.
3. **`layout/classic.ts`** : invariants (toute personne présente dans un nœud / aucune personne hors écran / enfants sur une génération > parents). Ce sont des assertions faciles à poser sur le résultat, et c'est la partie la plus volontairement complexe du projet.
4. **`repository.ts` — `validateFamilyData`** : round-trip import → export → import, migration v1/v2, doublons, unions fantômes.

## 5. Accessibilité et i18n

Les bases sont là : `aria-label` systématique sur les actions, `role="toolbar"` (`TreeCanvas.tsx:392`), `role="dialog" aria-modal="true"` sur les modales, `PersonCard` en `role="button" tabIndex={0}` avec Enter/Espace (`PersonCard.tsx:47-58`), `focus-visible` visible sur 5 sélecteurs (`styles.css:172,326,1384,1445,1468`).

**Important — contraste limite.** `--text-dim: #6e7787` sur fond `#14161a` (`styles.css:11`, usages aux lignes 91, 140, 152…) donne un contraste proche de 4:1 — calculé à la main, non mesuré à l'écran —, en dessous des 4,5:1 requis pour du texte à 14 px.

**Important — pas de focus-trap ni de retour de focus dans les modales.** Aucun des 4 dialogues (`PersonFormDialog`, `ResolutionDialog`, `EventDialog`, `DirectoryDialog`) ne piège Tab dans le dialogue ; il reste possible de tabuler vers l'arbre et la barre d'outils derrière, et le clic sur l'overlay (`onMouseDown` d'`PersonFormDialog.tsx:191`) ferme le dialogue sans restituer le focus à l'élément déclencheur. `autoFocus` n'est présent que sur le prénom (`PersonFormDialog.tsx:294`) et le champ de création de répertoire.

**Important — plusieurs modales s'ouvrent simultanément et se « volent » Escape.** Chaque dialogue ajoute son propre listener `window.keydown` (`PersonFormDialog.tsx:52-58`, `ResolutionDialog.tsx:25-31`) ; App en a un troisième pour désélectionner (`App.tsx:238-243`, arbitré par `!dialog && !pending`). Un même appui sur Escape ferme donc PersonFormDialog **et** EventDialog s'ils sont empilés. Pas de pile de modales.

**Important — le toast n'est pas annoncé.** `<div className="toast">` (`App.tsx:961`) sans `role="status"` ni `aria-live` : tous les retours (« Lien enregistré », « Personne supprimée »…) sont invisibles pour un lecteur d'écran.

**Mineur — pas de `prefers-reduced-motion`** dans `styles.css` (les seules `@media` sont des breakpoints de largeur).

**i18n** : tout est codé en dur en français, assumé (README : « L'interface et les commentaires de code sont en français »). Conséquence non cosmétique : le parseur de dates (`MONTHS`, `dates.ts:28-41`) ne reconnaît que les mois français — un arbre saisi dans une autre langue explosera. C'est un choix cohérent, pas du laxisme.

## 6. Dette évidente

**Important — code mort, dont une boucle vide.** `danglingPersonRefs` (`directories.ts:327-350`) n'est appelé nulle part (`serialize()` de `repository.ts:80` non plus) et contient, lignes 344-347, une boucle `for (const event of eventsOfPerson(...))` dont le corps ne fait qu'un `continue` — le corps a visiblement été nettoyé sans retirer la boucle. À supprimer, ou à transformer en test.

**Important — aucune sauvegarde / versionning automatique.** Le document n'existe qu'en une clé localStorage live. Le seul filet est « Exporter » manuel — protection repoussée sur l'utilisateur, c'est ce qui rend les blocs du point 3 bloquants plutôt qu'importants.

**Mineur — `.gitignore` contient une vingtaine d'entrées mortes** héritées de l'ancienne version (`*.db`, `*.ged`, `scans_bruts/`, `config.json`…), que ce projet n'utilise plus.

**Mineur — README vs code :** quasi alignés (localStorage `simple-family-tree:v3`, IndexedDB pour les octets — vérifié à `repository.ts:16` et `mediaStore.ts:16-18`). Seul point de vigilance : `syncDefaultLifeEvents` est appelé à 4 endroits (`operations.ts:291,326`, `repository.ts:255`…) — un futur chemin de mutation qui l'oublierait désynchroniserait les événements par défaut (le piège existe déjà via `SidePanel.patchPerson`, point 1).

**Aucun TODO/FIXME/HACK** dans `src/`.
